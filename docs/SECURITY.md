# Локальная проверка защиты

Дата: 19 октября 2026 года. Объект — собственное приложение, без проверки чужих сервисов. Автоматические запросы выполнялись через Fastify.inject на отдельных in-memory БД. Браузерный проход использует отдельный loopback-сервер, случайный порт, фиктивный пароль и синтетические записи; рабочая база и бот в нём не участвуют. Публичный tunnel не подвергался нагрузочным атакам, реальные пароли не отправлялись через него.

## Найдено и исправлено

1. Ограничение неправильных паролей раньше сбрасывалось при перезапуске и учитывало только IP. Теперь счётчики хранятся в SQLite: 8 неверных попыток с адреса / 15 минут и 30 суммарно для единственного аккаунта. Смена IP/логина не обходит общий лимит. Уже открытая сессия продолжает работать при блокировке входа.
2. Проверка доступа раньше выбирала финансовые пути регулярным выражением по сырому URL. Теперь onRequest-хук находится в отдельном Fastify plugin и применяется к сопоставленным API-маршрутам до разбора тела. Варианты URL дополнительно проверены. Уязвимость обхода в старой версии не подтверждена; устранена зависимость защиты от написания URL.
3. Не было общей защиты от частых запросов и явных сетевых таймаутов. Добавлены фиксированные окна с ограниченной памятью: 240 запросов/IP/минуту, 60 записей/IP/минуту, 60 login-запросов/минуту и 1200 запросов/процесс/минуту. Сначала проверяется общий лимит. Максимум 2048 счётчиков; при заполнении новые запросы получают 429. Лимит ответа включает Retry-After.
4. Добавлены ограничения тела 16 KiB, заголовков 10 секунд, запроса/неактивного соединения 15 секунд, keep-alive 5 секунд, 100 запросов на сокет и 200 одновременных соединений. Это уменьшает доступные ресурсы для злоупотребления, но не гарантирует защиту канала связи.
5. Проверка Origin теперь сравнивает нормализованный origin со схемой, отклоняет userinfo и учитывает Sec-Fetch-Site. Куки — HttpOnly/SameSite=Strict и Secure для HTTPS. Общий отказ при неверном логине/пароле не раскрывает существование аккаунта.
6. Production CSP разрешает скрипты только с текущего origin; inline theme-script перенесён в модуль. Запрещены object/embed, внешние формы и framing; настроены nosniff, Referrer-Policy, Permissions-Policy, CORP, HSTS при HTTPS и no-store. Inline CSS разрешён для Radix/Framer Motion; в dev разрешён inline JS для Vite.
7. Устранена неоднозначность разделителя при хешировании пары логин/пароль (теперь JSON-массив). При совпадающем времени создания сессий сохраняются 20 последних по времени и rowid. В БД хранятся SHA-256-хеши случайных 256-битных сессионных токенов; logout отзывает токен.
8. История больше не отдаёт неограниченный массив: совместимый запрос без параметров ограничен последними 100 платежами; страничный запрос — максимум 50, в интерфейсе 10. Курсоры ограничены длиной и валидируются; SQL остаётся параметризованным. Кеш браузера очищается при выходе/истечении сессии.

## Проверяемые сценарии

Запуск воспроизводимых серверных проверок: `npm ci && npm test`. Файлы: `tests/security.test.ts`, `tests/pagination.test.ts`, существующие API/service/bot-тесты. Браузерный стенд запускается отдельно из `/tmp` и не является зависимостью проекта; результаты — в `VERIFICATION.md`.

## Практические границы

Это проверка конкретных сценариев и усиление защиты приложения, не независимый полный пентест и не гарантия отсутствия уязвимостей. Объёмный DDoS, реальные slowloris-соединения, эксплуатация ОС/SQLite и чужая инфраструктура не атаковали. Сетевые таймауты проверены по настройкам сервера, не длительной атакой. У Cloudflare Quick Tunnel не настраивались пользовательские WAF-правила или защита по тарифу.

Лимит единственного аккаунта мешает распределённому подбору, но атакующий может временно заблокировать новый вход; действующие сессии при этом сохраняются. Для следующего этапа нужны второй фактор, мониторинг и правила на внешнем proxy. Минутные лимиты запросов находятся в памяти и сбрасываются при рестарте; счётчики неверных паролей сохраняются в SQLite. За доверенным локальным connector разрешены CF-заголовки; это не защита от пользователя, уже получившего доступ к самой машине.

Веб-режим без WEB_PASSWORD остаётся только для локальной разработки. Пароль задаёт владелец в .env; рекомендуется случайное значение. Персональные аккаунты и роли, аудит действий и проверяемое резервное восстановление требуют дальнейшей работы; месячная история тарифов уже реализована. Ранее переданные в чат токены остаются вне публикуемой Git-истории и сборки; их жизненным циклом управляет владелец аккаунтов. Проверка перед открытием репозитория описана в [PUBLICATION_AUDIT.md](PUBLICATION_AUDIT.md).

Подход сверен с первичными источниками: [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [OWASP Denial of Service Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Denial_of_Service_Cheat_Sheet.html), [Fastify Server reference](https://fastify.dev/docs/latest/Reference/Server/).
